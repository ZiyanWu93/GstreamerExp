GstreamerExp

A GStreamer-based streaming software stack with pluggable congestion control (SCReAM, GCC), loss recovery, and measurement. This page covers the system architecture, the runtime execution model, the programming model, and the pipelines, then tells each goal end to end — plan, status, and the hypotheses that are its evidence: Goal 1 (match UMN's stack) and Goal 2 (characterize SCReAM through its configuration space, answered by hypotheses H1–H7). Reference materials close it out.

2 · Programming model

Everything that affects pipeline behavior lives in a YAML spec. The runner reads the spec, validates it strictly, projects it into per-role dataclasses, and lets the worker assemble a Gst.Pipeline from those dataclasses. No knob is set inside the code — the spec is the single source of truth.

The five rules.  Pipeline first, experiments second.  Insights are functions of data, not frozen text.  Specs validate at load time.  No silent fallbacks.  A field gets a variant tag only when a second implementation exists; one variant stays a flat value.

Spec layers

Four directories under specs/, each one orthogonal to the others. A configuration composes a video and a network preset into a complete scenario; an experiment composes configurations into a comparison.

Field shapes: tagged vs flat

Rule 5 in practice. A field is tagged with a kind: discriminator only when two real variants exist; with one, it stays a flat value. The current shape:

FieldShape todayWhy
congestion_control.algorithm tagged: scream | gcc two real algorithms with disjoint parameters
source.backend tagged: synthetic | file two real backends today
loss.model tagged: none | uniform | bursty three real loss generators
codec flat scalar: vp8 only VP8 implemented; widen to a tag when a second codec lands

Verification contract

Every run is bracketed by checks: the spec's scenario.metrics list states what must be measured; reporting.py verifies each one was sampled. tools/network_probe.py empirically validates that the impairment tc applied matches the spec (so a Gilbert-Elliott burstiness claim can be checked against what actually flowed). State leaks (stranded tc qdiscs, orphaned workers) are bugs in the cleanup structure — every allocation registers its teardown atomically through ExitStack in runner.py.

3 · Execution model

How the pipelines from §1 actually run at the byte and millisecond level. Threading, time, controller scheduling, and the chain by which network impairment turns into a controller reaction.

Read order. §3.1 threads and the master clock. §3.2 buffer flow and what backpressure looks like. §3.3 the three clock domains the system juggles. §3.4 how SCReAM and GCC are scheduled at runtime. §3.5 when each recovery primitive fires and what it costs. §3.6 the impairment chain from tc qdisc to controller reaction. §3.7 a run from start to flush.

3.1 Threads and the master clock

A GStreamer pipeline runs as a small set of cooperating threads, one per branch boundary. Threads are decoupled at queue elements: every time a buffer crosses a queue, the upstream and downstream halves run on different threads with their own scheduling. In a SCReAM camera pipeline that means roughly four threads: the source / encoder branch, the payloader, the screamtx + rtpbin branch, and the udpsink.

Every pipeline owns a single GstClock. The clock is the shared timeline: every element schedules its work against it, and buffers carry presentation timestamps relative to it. On the sender, the source's clock is the master. On the receiver, the receiver's own clock drives display while the RTP timestamps on incoming buffers are translated into local clock time by the jitter buffer.

3.2 Buffer flow and backpressure

Data moves through the pipeline in push mode: the source emits buffers, each element forwards downstream. When a downstream queue fills, the upstream thread blocks on the next push. That is backpressure, and it is the only mechanism by which a slow link can throttle a fast encoder.

Why this matters for the comparison. In a Bare pipeline, udpsink cannot block on the network (UDP is non-blocking); it drops on socket-buffer overflow. A too-fast encoder produces losses, not backpressure. In a SCReAM pipeline, screamtx paces output: it observes the link state and refuses to release packets faster than the link can carry. The pacer is the backpressure point. In a GCC pipeline, rtpgccbwe only adjusts the encoder target; it does not pace at the transport. That is part of why the two controllers behave differently under burst.

3.3 Time: three clock domains

Three clocks live in the system. Joining them is how we measure.

  • Pipeline clock (GstClock). The element scheduler. Sets buffer PTS / DTS. Used for "when to play this frame" decisions.
  • RTP timestamp (90 kHz video clock). Stamped on every RTP packet by the payloader. Persists across the wire. Survives all of payloader / network / depayloader.
  • Wall clock. What latency probes record against. The thing we report to humans.

The eight-probe stage-latency metric works because every probe records (wall_clock, rtp_timestamp, byte_count). The RTP timestamp is the join key across endpoints: the sender's encoder.src probe at rtp_ts = T joins with the receiver's decoder.src probe at the same rtp_ts = T, giving end-to-end latency in wall-clock terms.

3.4 Controller scheduling

SCReAM

  • Runs on every RTCP feedback packet, ~50–100 ms cadence.
  • Each feedback updates RTT estimate, queue-delay estimate, in-flight bytes.
  • Decision output: current-max-bitrate notify on screamtx. The encoder picks it up at the next frame boundary.
  • Side effect: paces transmission. The transport-side rate limit is built in.

GCC

  • Runs on RFC 8888 TWCC feedback (per-packet arrival times) plus a periodic timer.
  • Each cycle: arrival-time gradient plus loss fraction → overuse / underuse signal → bitrate adjustment.
  • Decision output: estimated-bitrate property on rtpgccbwe, which the application maps to vp8enc.target-bitrate.
  • No transport pacing built in. Pure rate signal to the encoder.

One of the load-bearing asymmetries: SCReAM is a CC and a pacer; GCC is a CC only. When the network bursts, SCReAM smooths the outgoing traffic; GCC relies on the encoder's response time to do the same job.

3.5 Recovery timing

Each recovery primitive has a cost in time. Recovery is a budget against the jitter buffer's deadline.

  • NACK + RTX. The receiver's jitter buffer detects a sequence gap; NACK fires over RTCP; the sender's rtprtxsend retransmits the missing packet. Cost: one RTT plus the encoder-side queue. Within budget if jitter-buffer latency > RTT.
  • PLI. The receiver detects a decode-fatal gap and requests a keyframe. The sender's encoder forces one. Cost: RTT plus one encoder cycle. Heavy because the keyframe is large.
  • ULPFEC. Forward error correction. The receiver's rtpulpfecdec reconstructs lost media packets from the FEC matrix without a round trip. Cost: bandwidth overhead on the wire. Within budget only if the loss pattern fits the matrix; bursts past the matrix escape.
  • Jitter buffer. The wall-time budget for everything above. Configured by a latency knob. After that, the gap is given up on (or escalated to PLI).

3.6 Impairment effect chain

How a tc qdisc change on the sender's outgoing traffic turns into a controller decision. 

tc tbf (rate cap) + tc netem (delay, loss iid/GE)   ← spec-driven, on sender's outgoing traffic
          │
          ▼
[sender qdisc: backlog grows or drops]
          │ (1) udpsink fills socket buffer if tbf rate < encoder rate
          ▼
[RTP on wire: gaps from netem drops; delay added; rate capped by tbf]
          │
          ▼
[receiver jitter buffer: sees sequence gaps]
          │ (2) reports loss + arrival times via RTCP
          ▼
[RTCP back to sender]
          │
          ▼
[SCReAM: queue-delay + loss → reduce target] OR [GCC: TWCC gradient → reduce estimate]
          │ (3) ~50–200 ms after the first lost packet
          ▼
[vp8enc: next frame uses new target-bitrate]

Three things to keep in mind. (1) The sender sees the qdisc backlog but not the wire-level drops directly; the wire's truth comes back via RTCP. (2) RTCP cadence sets the controller's reaction floor: even a perfect controller cannot react faster than feedback arrives. (3) The encoder reacts at frame boundaries, not at decision instants. At 30 fps, that is up to 33 ms of inertia after the controller has already decided.

3.7 Run lifecycle

How a single run executes, from spec load to flush.

  • Setup. Spec is validated, the pipeline is assembled from the three shapes, tc qdiscs are applied to the configured interface, both halves go to PAUSED and then PLAYING.
  • Steady state. Data flows. The runner main thread drives the during_run hooks, applying impairment changes at scheduled wall-clock points. Probes accumulate in memory.
  • End. The source signals EOS, or a run timer fires. The pipeline drains downstream; both ends process the final buffers. Probes flush to JSONL. The tc qdisc is cleared.
  • Failure. Any element error or unexpected EOS bubbles up via the bus. The runner cleans the qdisc and exits non-zero. The verifier then evaluates the partial output against the hypothesis's pass / fail rule.

1 · System architecture

The architectural shape of GstreamerExp. Two endpoints (vehicle host and operator host) connected by standard RTP / RTCP / SRTP / DTLS, plus one orchestrator (Session runtime) plus one external integration surface (ControlPort). Each pipeline box has a named contract (Source, Encoder, Sink, ClockSync, RTPMeta, Session, ControlPort): an interface with a today-implementation (synthetic source, software VP8, measurement sink) and a tomorrow-implementation (real camera, hardware H.264, display sink). The architecture stays fixed as the product evolves; §5 (the roadmap) is about which contract implementations are stubs and how they fill in.

Read order. §1.1 the actors and what is in versus out of repo. §1.2 processes and how they are deployed. §1.3 the actual GStreamer element graph on each endpoint. §1.4 what is on the wire. §1.5–§1.6 the architectural choices that are real calls, not defaults. §1.7 the decisions recorded as one-line claims.

1.2 Process and deployment model

One process per role. Configured by spec, supervised externally.

gstexp camera

on the vehicle host

  • One GStreamer pipeline assembling N parallel send chains under a single rtpbin (see §1.5 for the multi-stream choice).
  • Owns the camera-side clock domain.
  • Runs ForensicSink locally.
  • Exposes a status surface used by the Session runtime.

gstexp viewer

on the operator host

  • Receives N streams, decodes, composites mosaic, renders to DisplaySink.
  • Owns the operator-side clock domain.
  • Runs its own ForensicSink; the receiver-side bytes are byte-identical to the sender's.
  • Drives RTCP feedback (NACK, PLI) back to the camera.

gstexp session

orchestrator (anywhere)

  • Holds the spec, supervises camera and viewer processes.
  • Serves the status endpoint (JSON / WebSocket) for the operator UI.
  • Serves the ControlPort for external systems.
  • Owns session lifecycle: start, run, stop, replay.

Packaging

how it ships

  • Python wheel installed into a venv. No container required.
  • systemd units for the three processes (gstexp-camera.service, gstexp-viewer.service, gstexp-session.service).
  • Optional Dockerfile for reproducibility.
  • Specs are YAML files versioned alongside the code.

1.4 Wire architecture

Four channels. Each does one thing.

1 · Data plane (RTP/UDP, one SSRC per stream)

  • RTP header extensions carry: absolute capture timestamp, source frame id, optional geo (lat / lon / RTK status).
  • Payload is whatever the codec produces.
  • SRTP / DTLS-encrypted when secure: true in spec.

2 · Path feedback (RTCP)

  • Standards-compliant. NACK, PLI, RTCP-FB.
  • SCReAM consumes RTCP and its own per-packet feedback over the same RTCP socket.
  • GCC consumes the RFC 8888 transport-wide congestion control feedback messages.
  • This is the channel UMN replaced with custom RFBK. We don't.

3 · Control plane (ControlPort)

  • Separate connection. Default: gRPC over QUIC or TCP. Zenoh is a real alternative (UMN uses it) but adds a runtime dependency that gRPC does not.
  • Operations: request_keyframe, switch_active_camera, push_policy, get_session_status, stream_metrics, start_session, stop_session.
  • Lives on the Session runtime. Does not touch the data plane directly; policy updates go through the Session, which reconfigures the pipeline.

4 · Forensic plane (local only)

  • Each endpoint writes its ForensicSink to local disk. No network involved.
  • Encoded bytes only, no re-encode. Sender and receiver files are byte-identical for every delivered frame.
  • Sidecar metadata: codec, framerate, RTP extension map.

1.5 Multi-stream architecture (a real call)

Teleop typically runs three to six cameras. There are two clean ways to model that, and the choice has real consequences.

(A) One pipeline, N parallel chains

  • Single rtpbin, N SSRCs, shared clock, shared CC instance.
  • The allocator (priority-ordered degradation) sits as a layer above CC and adjusts per-stream encoder targets through the Encoder contract.
  • Pros. Single clock domain. CC sees aggregate link state. Simpler config. Lower process overhead.
  • Cons. One bad camera can stall the whole pipeline. Crash-isolation is process-level only.

(B) N independent pipelines

  • Per-camera process or per-camera bin. Per-stream CC.
  • Needs a cross-pipeline allocator to coordinate priorities, which is harder than (A)'s in-pipeline allocator.
  • Pros. Crash-isolated. Hot-restart a single camera without touching the others.
  • Cons. N CC instances, all competing for the same link, with no shared signal. UMN ships this shape and the coordination layer it lacks shows up as the BandwidthAllocator.

Default: (A). One pipeline, N chains, one CC, allocator above it. Move to (B) only if cross-camera failure isolation becomes a hard requirement — at which point the Encoder contract and the policy-driven allocator are already where they need to be for the split to land cleanly.

1.6 Control plane and clock domain

Control plane (ControlPort)

The protocol that external systems use to talk to the streamer. 

request_keyframe(stream_id)        → ack
switch_active_camera(stream_id)    → ack
push_policy(policy_yaml)           → ack
get_session_status()               → SessionStatus
stream_metrics()                   → stream<Metrics>
start_session(spec)                → session_id
stop_session(session_id)           → ack
  • Implemented by Session runtime. Pipeline reconfigures happen through the Session, not from outside.
  • Schema is part of the spec model. Versioned.
  • Decoupled from data plane. Debuggable, replaceable, testable.

Clock domain

One clock domain per endpoint, ideally PTP-aligned across both.

  • Every frame carries an absolute capture timestamp in an RTP header extension.
  • The ClockSync agent on each endpoint measures and exposes the offset. Every metric record carries it.
  • Glass-to-glass latency is display_ts − offset_corrected_capture_ts, computed from the header extension, not from local-only probes.
  • Fallback: NTP plus a UDP exchange like UMN's TREQ/TRES. Architecture does not change; precision degrades from sub-millisecond to several milliseconds.

1.7 Architecture decisions, recorded

One-line claims. Each marks a place where we are choosing one of several possible architectures, on purpose, with a reason.

  • RTP, not custom UDP. Inherits SRTP / DTLS / RTCP / standards-compliant analyzers. UMN's custom framing is the opposite direction; we explicitly do not follow it.
  • One process per role, not per stream. Camera, viewer, session runtime. Shared clock domain per endpoint. Multi-stream is N chains in one pipeline, not N processes (see §1.5 (A)).
  • Contracts are code, not just docs. Each Source / Encoder / Sink / ClockSync / RTPMeta / Session / ControlPort is a Python protocol with a runtime registry. Spec selects an implementation by name.
  • Control plane is not in this repo. Vehicle controls, RAN telemetry, and trajectory are external systems that talk to the streamer through ControlPort. UMN's monorepo conflates two products.
  • Measurement is a Sink, not a side feature. Decoded PSNR, eight-probe stage latency, and glass-to-glass latency ship on by default. The product is its own regression harness.
  • Forensic record is dual-end and lossless. tee off encoded bytes on both endpoints. No re-encode. Sender and receiver files match byte-for-byte on every delivered frame.
  • Single CC, multi-stream allocator above it. One SCReAM or GCC instance per pipeline; the allocator translates the shared rate into per-stream encoder targets through the Encoder contract. (See §1.5.)
  • Absolute time on the wire, not just local probes. Glass-to-glass latency derives from the RTP-header-extension capture timestamp plus the ClockSync offset, not from a chain of pipeline-local probes.

5 · Goals

GstreamerExp has two goals pulling together. Goal 1 (§6) is an engineering goal: match the capabilities UMN's teleop stack ships, while keeping the standards transport and controller rigour we do better. Goal 2 (§7) is a research goal: characterize how SCReAM behaves across its configuration space. Each goal below is told end to end — plan, status, and the hypotheses that are the evidence.

5.1 The two goals

Stating them separately keeps the work honest about what is engineering and what is research.

Goal 1 · Match UMN's stack, keep our advantages

Engineering deliverable.

Match the capabilities UMN's Teleop-Gopher-Streamer (GopherNetLab) ships today: real cameras with hardware-timestamp metadata, multi-codec with hardware-encode paths (NVENC / QSV / VAAPI), multi-stream rigs of three to six cameras, adaptive resolution, partial-frame decode at the receiver, dual-end forensic bitstream recording, an external integration surface for vehicle / RAN / trajectory.

Keep what GstreamerExp does better than UMN: standards RTP / RTCP / SRTP / DTLS instead of UMN's custom UDP framing; reference congestion-control implementations (Ericsson SCReAM via gstscream, rtpgccbwe for GCC) instead of UMN's 226-line AIMD reimplementation; packet pacing; the full loss-recovery toolbox (NACK + RTX, PLI, ULPFEC); and the measurement rigour (decoded PSNR, eight-probe stage latency, declarative validated specs, hypothesis framework with pass / fail verifiers).

See the side-by-side comparison in the UMN design doc for the full inventory. Gaps map onto Goal 1's capabilities (§6.1), grouped by seven contracts (Source, Encoder, Sink, ClockSync, RTPMeta, Session, ControlPort) that mark where each gap closes.

Goal 2 · Characterize SCReAM through the configuration space

Research deliverable.

Map how SCReAM behaves across the configuration knobs documented in §7.2 and the network conditions that engineer those knobs. Until that map exists, claims like "SCReAM beats GCC on a particular network" only carry as far as the few cells we have run.

Gaps live in our characterization (§7): knob-sensitivity sweeps, network-condition sweeps, mechanism-isolation experiments, interaction studies, boundary behaviour.

Both goals reduce to gap identification. Functional gaps say what to build. Characterization gaps say what to test. §5.2 covers how they share work.

5.2 How the two goals relate

The two goals are complementary, not independent.

Goal 1 broadens what Goal 2 can sweep

Multi-codec, multi-stream, hardware encode, real cameras all become axes Goal 2 can vary. Until the Encoder contract lands a second codec, "SCReAM × codec" is uncharacterizable. Until multi-stream lands, "SCReAM with shared vs per-stream instances" is uncharacterizable.

Goal 2 sharpens what Goal 1's stack can claim

A fuller stack is only useful if the claims it produces are believable. The characterization sweeps tell us where to trust "SCReAM beats GCC on X" and where the claim does not carry yet. Without Goal 2, Goal 1 drifts toward "feature parity with UMN," which is not the point.

Two practical implications.

  • A Goal-2 dimension is sometimes blocked on a Goal-1 capability. The dependency goes one way: building the codec contract unblocks the SCReAM × codec sweep, not the reverse. Sequencing matters.
  • Goal-1 work needs a Goal-2 question to shape it. "Add H.264" is not a hypothesis; "does SCReAM's queue-delay target need different values for VP8 vs H.264?" is. Pick a Goal-1 sprint because it unblocks a Goal-2 question, not just because UMN ships the feature.

5.3 What this drops, what it keeps

Drops, on purpose

  • UMN's monorepo shape (streamer plus vehicle controls plus RAN plus trajectory in one repo). Convenient for a research demo. Wrong for a product.
  • Custom UDP framing. Standard RTP keeps SRTP / DTLS / RTCP / standard analyzers in reach.

Keeps, no regression

  • Hypothesis framework, validated specs, declarative network impairment, per-stage latency probes, decoded PSNR.
  • All of the above continue to run on the same code path the product runs. They become the product's regression harness.

5.4 Open strategic question — the repo shape

Two viable shapes for the repo as the product matures. This is a real call, not a default.

(a) Evolve in place. GstreamerExp grows the seven contracts and becomes the product. Testbed and product share one repo. Every experiment doubles as a regression test on the product. Cheaper. Tighter coupling between research and shipped behavior.

(b) Spin off. Keep GstreamerExp pure as a CC research instrument. Start a sibling repo (teleop-streamer or similar) that depends on the same pipeline modules. Lets the product churn without destabilizing the research baseline. Costs a second CI surface and a packaging boundary.

Default until proven otherwise. (a) until the product needs branch protection or release cadence the research baseline cannot tolerate. At that point, split. The seven contracts in §6.1 are the natural cleave line if (b) becomes necessary.

Quick reference — knobs and dimensions in scope

SCReAM knobs

  • min-bitrate / initial-bitrate / max-bitrate. Hard rails on the encoder target.
  • queue-delay-target. Buffering threshold above which SCReAM backs off. Single most influential delay knob.
  • Loss backoff. Multiplier applied when loss is detected.
  • Bandwidth headroom. Fraction of estimated capacity kept as safety margin.
  • Pacing. max-bytes-in-flight, smoothing window; caps how many bytes SCReAM permits in flight.
  • ECN / L4S. Explicit congestion notification, on or off.
  • RTCP feedback cadence. Peer-side; gates SCReAM's reaction floor.

Environment dimensions

  • Link capacity. Static cap or time-varying (static / slow / fast / step / 5G trace).
  • RTT. Constant base latency on the path.
  • Jitter. Per-packet delay variance.
  • Loss pattern. iid (uniform) or Gilbert-Elliott bursty.
  • Workload. Bitrate envelope of the encoded stream that SCReAM regulates.

7.6 Mechanism contributions

SCReAM does several things at once (rate adjustment, pacing, feedback-driven adaptation). Three targeted studies isolate which mechanism contributes what to its observed advantage.

  • Pacing vs encoder-rate adjustment. SCReAM does both. We do not know the relative contribution of each to the SCReAM-over-GCC delta. Needs a gstscream flag to disable pacing.
  • Controller → encoder coupling fidelity. H5 isolated the coupling gap at UMN but did not measure how tight the coupling needs to be to recover the gap. The "applied-bitrate fidelity → CC outcome" sensitivity curve is missing. Needs an instrumented delay / drop knob on the current-max-bitrate notify path.
  • Feedback cadence dependency. Vary RTCP-feedback interval (50 ms / 100 ms / 250 ms / 500 ms / 1 s) on a wobbly-bandwidth network to find SCReAM's reaction floor.

  • Single-host loopback reproduces the bandwidth and the delay faithfully but not real 5G radio effects like interference or radio-layer retransmits.
  • We measured how much of the link each side uses, not how good the picture looks. "Uses the link better" is a bandwidth claim, not yet a video-quality claim.
  • UMN's controller is an early reimplementation (its own code marks receiver feedback as future work). This is a snapshot of branch 502533c, not a general statement about SCReAM.
  • We did not measure UMN's deployed hardware (NVENC) encoder. From reading the code we believe the same wiring problem affects it, but a real NVIDIA box would be the honest confirmation.
  • Measuring picture quality (PSNR or SSIM of the received video vs the source on both sides) is the next verification step.

7.7 Interactions with other features

How SCReAM behaves when the rest of the stack changes around it. These are the sweeps gated by Goal 1 capabilities.

  • SCReAM × codec. Does the queue-delay target need different values for VP8 vs H.264? Unknown until §6.1's Encoder contract supports two codecs. Blocked on Goal 1 sprint 1.
  • SCReAM × recovery. NACK + RTX retransmits and ULPFEC bytes pass through the controller's view. We have not measured how they bias SCReAM's decisions. Runnable today as a 2 × 2 × 2 cross-product over the three recovery primitives.
  • SCReAM × multi-stream. One CC instance for N streams vs N independent instances. Blocked on the multi-stream refactor.

7.8 Boundary behaviour

Where does SCReAM stop behaving like SCReAM and start degenerating? Binary-search the threshold in each of RTT, loss, and jitter at which the SCReAM-over-bare advantage collapses.

  • RTT degeneration threshold (sweep base RTT, find the inflection point).
  • Loss-rate degeneration threshold (sweep iid loss until SCReAM ≈ bare).
  • Jitter degeneration threshold (sweep netem jitter until SCReAM gain disappears).

Each subgoal above is a hypothesis-spec family that can be authored against the existing framework. The work is proposal-driven, not platform-driven: pick a subgoal, formulate the hypothesis with a falsifiable verifier, run the sweep, write the result.

7.9 What's next — the plan

Three knob sweeps now agree: SCReAM's tuning knobs move latency, not picture quality, for this workload, and a more aggressive setting slightly hurts. So the next steps are not "more knobs." They are the things that make that finding trustworthy and map where SCReAM actually breaks. Four phases, each a small family of hypotheses in the existing framework. Phases 1–3 run on the current testbed; phase 4 waits on Goal 1.

Phase 1 · Make the knob finding trustworthy (partly runnable)

  • A second video — not feasible right now: realmotion-avi is the only real recorded clip available, and synthetic patterns are ruled out. Parked until a harder clip exists.
  • A sharper quality measure. Add a windowed post-step PSNR (and optionally SSIM) so a recovery effect that whole-run averages wash out cannot hide. Per-frame PSNR is already recorded, so this needs no new run.

Phase 2 · Find where SCReAM breaks (in progress)

  • Delay (RTT) boundary mapped: usable to ~200 ms one-way delay, cliff by 400 ms (H9).
  • Loss boundary mapped: with recovery off, delivery collapses below 0.1% loss (H10) — a direct case for loss recovery.
  • Jitter boundary ran but came back inconclusive — netem reordering collapses delivery at any jitter with recovery off (H11).
  • Recovery-on loss re-run done (H12): recovery does not lift the loss cliff — an important negative that redirects the work.
  • Isolate why loss collapses delivery (jitter-buffer drop policy vs the complete-frame metric vs a SCReAM-under-loss interaction) — now the real open question. Plus a reorder-controlled jitter re-run for H11.

Phase 3 · Breadth (runnable now)

  • Network axes largely covered by the boundary sweeps: delay (H9) and jitter (H11, inconclusive) done; only the bursty Gilbert-Elliott matched-mean loss comparison remains (§7.5).
  • The loss-recovery cross-product (NACK/RTX × PLI × FEC) and how it biases SCReAM — H12 did NACK+PLI under loss; the full 2×2×2 still open (§7.7).

Phase 4 · Blocked on Goal 1

  • SCReAM × codec (VP8 vs H.264) — needs the Encoder contract.
  • SCReAM × multi-stream — needs the multi-stream refactor.

Recommended first move: Phase 1's second-video run. It is what turns "the knobs do not matter" from a one-clip observation into a finding we can stand behind.
