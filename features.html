GstreamerExp — Features & Roadmap

A reading map of how the testbed is organized today: the programming model, the three pipeline shapes that exist, the configuration surface for SCReAM and GCC, and the gaps between this testbed and a real teleoperation video stack.

1 · Programming model

Everything that affects pipeline behavior lives in a YAML spec. The runner reads the spec, validates it strictly, projects it into per-role dataclasses, and lets the worker assemble a Gst.Pipeline from those dataclasses. No knob is set inside the code — the spec is the single source of truth.

The five rules.  Pipeline first, experiments second.  Insights are functions of data, not frozen text.  Specs validate at load time.  No silent fallbacks.  Two implementations make a pattern; one implementation just uses one shape.

Spec layers

Four directories under specs/, each one orthogonal to the others. A configuration composes a video and a network preset into a complete scenario; an experiment composes configurations into a comparison.

LayerWhat it declaresHow it's referenced
specs/videos/ Source preset — backend (synthetic/file), dimensions, fps, num_frames video: ball-480p15 in a configuration
specs/networks/ Impairment preset — list of tc steps (rate, delay, loss) over time network: fluctuating-5mbps-300kbps in a configuration
specs/configurations/ Per-run scenario — codec, encoder, transport, CC, recovery, sink, actors cli.py 8 runs configuration 8.yaml
specs/experiments/ Named comparison — list of configurations + varies: whitelist of paths that may differ experiment.py scream-vs-gcc-720p

From spec to pipeline

cli.py is the entry point for a single run. The flow: 

YAML configuration
    │
    ▼   validation.py
    │   ──────────────
    │   • strict schema check (typos at any level fail here)
    │   • cross-field rules  (e.g. recovery.nack=True ⇒ rtx_buffer_ms required)
    │   • resolve refs       (video: → source block, network: → step list)
    │
    ▼   validation.project_to_roles()
    │   ────────────────────────────
    │   one unified spec  →  Camera dataclass + Viewer dataclass
    │                        (peer hosts, ports, codec object injected)
    │
    ▼   runner.py        (local or distributed via SSH; ExitStack teardown)
    │   • runs `pre_run`  hooks (e.g. tc qdisc setup)
    │   • spawns worker.py on each actor
    │   • runs `during_run` hooks at scheduled offsets (e.g. tc step changes)
    │   • runs `post_run` hooks (cleanup)
    │   • fetches result files; writes runs/<id>/<ts>/summary.json
    │
    ▼   worker.py
        • camera.py / viewer.py build a Gst.Pipeline from the dataclass
        • metrics.py attaches pad probes per scenario.metrics
        • GLib main loop runs until num_frames or EOS

The "two implementations" rule

A field is tagged with a kind: discriminator only when two real variants exist. With one variant, it stays flat. The current shape:

FieldShape todayWhy
congestion_control.algorithm tagged: scream | gcc two real algorithms with disjoint parameters
source.backend tagged: synthetic | file two real backends today
loss.model tagged: none | uniform | bursty three real loss generators
codec flat scalar: vp8 only VP8 implemented; widen to a tag when a second codec lands
rate_kbps, delay_ms flat scalar one rate / delay model today (TBF cap, fixed delay)

Verification contract

Every run is bracketed by checks: the spec's scenario.metrics list states what must be measured; reporting.py verifies each one was sampled. tools/network_probe.py empirically validates that the impairment tc applied matches the spec (so a Gilbert-Elliott burstiness claim can be checked against what actually flowed). State leaks (stranded tc qdiscs, orphaned workers) are bugs in the cleanup structure — every allocation registers its teardown atomically through ExitStack in runner.py.

2 · Existing pipelines

Three pipeline shapes, dispatched at build time from spec.congestion_control. Both halves — camera (sender) and viewer (receiver) — have the matching shape on each side. Recovery elements (NACK+RTX, PLI, ULPFEC) are orthogonal: any combination is wireable into any of the three shapes.

media congestion control recovery transport

Bare baseline

No congestion control. Encoder is pinned at encoder.bitrate_kbps. Used as the reference shape: everything else is "bare plus a controller plus optional recovery."

camera (sender)

videotestsrc → caps → vp8enc → rtpvp8pay → udpsink

viewer (receiver)

udpsrc → caps → rtpvp8depay → vp8dec → videoconvert → fakesink

SCReAM delay-based

screamtx sits between payloader and udpsink and drives vp8enc.target-bitrate via its current-max-bitrate notify. RTCP feedback flows back from the viewer's screamrx through a separate udpsrc/udpsink pair on the camera.

camera (sender)

videotestsrc → vp8enc → rtpvp8pay → screamtx → rtpbin → udpsink
                                              ▲
                                              │  RTCP feedback
              udpsrc (rtcp_port) → rtpbin ─────┘

viewer (receiver)

udpsrc → screamrx → rtpbin → rtpvp8depay → vp8dec → fakesink
                          │
                          ▼  RTCP back to camera
                      funnel → udpsink

GCC loss + delay

rtpgccbwe sits in front of rtpbin and reads TWCC feedback to estimate the bottleneck rate. Each outgoing RTP packet carries a transport-wide sequence number (TWCC RTP header extension); the viewer's rtpbin generates the feedback packets itself — no custom receiver-side estimator.

camera (sender)

videotestsrc → vp8enc → rtpvp8pay [+TWCC ext] → rtpgccbwe → rtpbin → udpsink
                                                              ▲
                                                              │  TWCC RTCP
                                  udpsrc (rtcp_port) → rtpbin ──┘

viewer (receiver)

udpsrc → rtpbin (twcc-feedback-interval) → rtpvp8depay → vp8dec → fakesink
                  │
                  ▼  TWCC feedback back to camera
              udpsink

Recovery (orthogonal) composable

Any of the three shapes can be augmented with NACK+RTX, PLI, and ULPFEC independently. Three primitives, each landed and tested.

camera-side additions

  • rtprtxsend — ring buffer for retransmissions; depth = rtx_buffer_ms
  • rtpulpfecenc — proactive FEC repair packets at fec_percentage overhead
  • AVPF profile flag — required when nack or pli is on

viewer-side additions

  • rtprtxreceive — RTX→media PT demux + rtpbin do-retransmission
  • rtpstorage + rtpulpfecdec — sliding-window FEC recovery (no feedback round-trip)
  • rtpbin do-lost — emits keyframe-request events that become outbound PLI RTCP
  • jitter-buffer latency: 200 ms with NACK, 10 ms without

3 · Configuration space — SCReAM vs GCC

Each algorithm is exposed in full so the testbed can study performance implications across every meaningful knob. Bitrate bounds (init / min / max) are required because we always intend to pick them. Algorithm-specific knobs are Optional: absence in the spec means "no override, let the algorithm use its documented default." Defaults live with the algorithms, never in this project's code.

Shared by both

congestion_control.min_bitrate_kbpsfloor — controller will not drop below this

SCReAM viewer side

The current gstscream plugin's screamrx element exposes no GObject properties — ackDiff and nReportedRtpPackets are baked into the C++ constructor. Extending the plugin would unlock these knobs.

GCC camera side

Mapped to rtpgccbwe GObject properties. Far smaller surface than SCReAM — most of GCC's behavior is hard-coded inside the rtpgccbwe element today.

YAML fieldPropertyDefault
estimatorestimatorkalman (alt: linear-regression)

GCC viewer side

YAML fieldPropertyDefault
twcc_feedback_interval_msrtpbin.twcc-feedback-interval100 ms

Why so few knobs?

GCC has internal parameters (Kalman filter gains, trendline window, overuse threshold adaptation) that aren't surfaced as GStreamer properties. To study them, the rtpgccbwe Rust source would need to expose them as GObject properties first.

4 · Features to do

What's currently in scope: VP8 → RTP → (SCReAM | GCC | bare) → UDP over loopback or between two real hosts, with tc tbf + netem impairment (uniform iid or Gilbert-Elliott bursty loss) driven by during_run hooks. Recovery primitives NACK+RTX, PLI, and ULPFEC are implemented and orthogonal. Per-frame Y-plane PSNR against a reproduced source is the working quality metric. Below: gaps between this testbed and an actual teleoperation video stack, ignoring the operator-control return path.

DONE TODO

Capture

  • Real video from vehicle cameras (replace videotestsrc)
  • Multi-camera support (front / rear / sides; teleop typically ≥3 streams)
  • Hardware encoder on the vehicle side (V4L2 / NVENC / VAAPI)
  • Camera timestamp / frame-clock metadata (for sensor fusion, AR overlays, replay)
  • Camera calibration intrinsics/extrinsics passthrough

Encoding

  • Hardware-accelerated encoding path
  • Adaptive resolution — drop from 720p to 480p/360p when the rate-controller cuts the bitrate budget below the threshold where the higher resolution can hold quality. vp8enc currently has only target-bitrate as a knob, so under tight bottlenecks it produces blocky 720p (worst-case ~10 dB PSNR observed) instead of clean 360p. Encoder-side control loop driven by SCReAM's current-max-bitrate notify or GCC's estimated-bitrate; reconfigures vp8enc + the source capsfilter via runtime renegotiation.
  • Region-of-interest / variable quality across the frame (more bits on the road, fewer on the sky)
  • Scene-change detection and forced-keyframe-on-cut
  • HDR / wide-color-gamut preservation (taillight visibility, low-light scenes)

Transport

  • Encryption (SRTP / DTLS)
  • Authentication (operator station identity)
  • Redundant transport / multi-path (LTE + 5G failover)
  • Per-stream priority / DSCP marking
  • Loss recovery on top of SCReAM: NACK+RTX, PLI, ULPFEC — all three landed and orthogonal

Reception

  • Real display sink (replace fakesink with glimagesink / direct framebuffer / HMD)
  • Display sync (VSYNC alignment so frames present without tearing)
  • Per-camera composited view (mosaic / picture-in-picture)
  • Multi-stream synchronization across cameras (so they show the same instant)

Latency

  • Glass-to-glass latency measurement (capture → display) — the headline metric for teleop
  • Per-stage latency attribution — stage_latency metric, 8 probes (encoder.sink/src, pay.src, udpsink.sink, udpsrc.src, depay.src, decoder.sink/src, convert.src) joined by RTP timestamp; analysis/dimensions/latency.py surfaces per-stage durations
  • Latency-budget enforcement (drop frames when budget exceeded, don't queue)
  • Operator-side jitter buffer with explicit depth and policy

Quality

  • Per-frame quality metric — decoded_psnr (Y-plane PSNR vs reproduced source); SSIM / VMAF still missing
  • Quality degradation indicator surfaced to the operator UI
  • Audit-grade frame loss accounting (which frames, when, why)

Audio

  • Ambient audio from the vehicle (sirens, horns, impacts) — often safety-relevant

Recording / forensics

  • On-vehicle and on-operator recording of the actual streamed bitstream (for incident replay)
  • Synchronized multi-camera + telemetry capture
  • Lossless local copy alongside the lossy transmitted copy (so post-incident analysis isn't degraded)

Synchronization

  • Vehicle wall-clock timestamps in RTP headers (NTP / PTP-aligned)
  • Cross-stream sync (camera N's frame at time T arrives with the same T across all cameras)

Resilience to loss

  • Decoder error concealment / freeze-on-bad-frame strategy
  • Keyframe-on-loss request from receiver — PLI wired both sides (do-lost on rtpjitterbuffer → AVPF feedback)
  • Per-packet retransmit on loss — NACK+RTX wired via rtprtxsend / rtprtxreceive
  • Proactive redundancy on the wire — ULPFEC (rtpulpfecenc on camera, rtpstorage + rtpulpfecdec on viewer)
  • I-frame frequency tuned to recovery time, not just to bitrate efficiency
