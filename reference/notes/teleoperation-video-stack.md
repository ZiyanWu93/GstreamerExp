# Teleoperation Video Streaming Stack

## What It Is

The concrete end-to-end system that carries compressed video from a teleoperated vehicle to a remote operator station. Composed of adapter components that integrate open-source libraries (SCReAM, GStreamer, etc.) into a unified pipeline matching the architecture described by Teleoperation Video Transport.

## Why It Matters

Teleoperation Video Transport describes the conceptual architecture: what components are needed and how they interact. This note covers the actual running system that implements that architecture by selecting, configuring, and adapting real libraries and frameworks. Without a concrete stack, the conceptual architecture remains a design document with no executable form.

## Notes

## Introduction

Between a camera on a teleoperated vehicle and a display at the operator station lie at least seven processing stages and one unreliable cellular network. Each stage has mature open-source implementations, but assembling them into a system that delivers sub-150ms glass-to-glass latency over a link whose bandwidth changes by an order of magnitude between cell handovers is not a library selection problem. It is an integration problem: every buffer boundary between stages adds latency, every mismatch between the encoder's output rate and the network's carrying capacity causes either congestion or underutilization, and the feedback loop that connects network observations back to encoder rate control must close within a single round-trip time or the system oscillates.

[Teleoperation Video Streaming Stack](teleoperation-video-stack.md) solves this by implementing the architecture described in Teleoperation Video Transport through adapter components that bridge conceptual interfaces to concrete libraries. [GStreamer](gstreamer-overview.md) provides the pipeline framework that chains capture, encoding, transport, decoding, and rendering into a directed processing graph. SCReAM V2, integrated through its GStreamer plugin, governs the sending rate via self-clocked congestion control, pacing each RTP packet's release based on acknowledgment feedback rather than bandwidth estimation. Hardware video codecs (NVENC, VAAPI, ARM VPU) keep encoding and decoding latency below the frame interval. Raw UDP sockets with ECN codepoint handling provide the L4S-capable network layer that SCReAM needs for its lowest-latency operating mode. The adapter pattern keeps each library choice independently replaceable: SCReAM could be swapped for Google GCC, GStreamer for FFmpeg, or one hardware codec for another, without restructuring the overall system.

## Background

A teleoperation video streaming stack must chain together at least seven distinct processing stages: camera capture, color space conversion, video encoding, RTP packetization, network transport, RTP depacketization, video decoding, and display rendering. Each stage has mature open-source implementations, but integrating them into a system that meets teleoperation latency constraints (sub-150ms glass-to-glass) requires careful control of buffering at every boundary. [GStreamer](gstreamer-overview.md) provides the pipeline framework that connects these stages: each processing step is a GStreamer element, and elements are linked into a directed graph through which media buffers flow. The framework handles threading, buffer management, clock synchronization, and format negotiation between elements, freeing the application from low-level media plumbing.

SCReAM enters the pipeline through the gstscream GStreamer plugin, which acts as a gate between the RTP payloader and the UDP sink. The plugin holds RTP packets in SCReAM's sender-side queue and releases them only when the congestion controller's pacing schedule permits, implementing the self-clocking principle within GStreamer's data flow model. On the receiver side, ScreamRx processes incoming RTP packets and generates RTCP feedback that is sent back to the vehicle. The feedback loop closes when ScreamV2Tx on the vehicle processes the RTCP message and updates its congestion window, which in turn adjusts both the pacing rate and the target bitrate fed back to the encoder.

Hardware video codecs are essential for teleoperation because software encoding at the required resolutions (1080p or higher) and frame rates (30-60 fps) would consume too much CPU and introduce too much latency. Modern GPUs (NVIDIA NVENC), integrated graphics (Intel VAAPI/QSV), and embedded VPUs (ARM Mali, Qualcomm Venus) provide dedicated encoding and decoding hardware accessible through GStreamer elements. The encoder must support dynamic bitrate adjustment (responding to SCReAM's rate targets) and on-demand keyframe insertion (responding to SCReAM's loss signals), both of which require the codec adapter to translate between SCReAM's feedback interface and the hardware encoder's rate control API.

The network transport uses raw UDP sockets rather than TCP or QUIC to avoid head-of-line blocking and retransmission delays. For L4S operation, the sending socket must set the ECT(1) DSCP codepoint on outgoing packets, and the receiving socket must read the ECN bits from incoming packets using the recvmsg() system call with the IP_RECVTOS socket option. These ECN bits are the raw material that ScreamRx uses to generate the marking fraction that drives L4S congestion response.

## Problem

Five categories of demand arrive at the streaming stack. The most continuous is the stream of raw camera frames from the vehicle's camera sensor, arriving at the capture frame rate. Each frame must traverse the entire pipeline (encode, packetize, pace, transmit, receive, depacketize, decode, render) within the latency budget. The pipeline is only as fast as its slowest stage, and any stage that introduces buffering beyond one frame period adds directly to end-to-end latency. The GStreamer pipeline must therefore be configured for zero-copy buffer passing where possible, with encoder and decoder elements operating in low-latency mode that trades compression efficiency for speed.

The second demand is the stream of UDP datagrams arriving at the operator station. Each datagram carries one RTP packet that must be demultiplexed (extracting SSRC and sequence number), have its ECN codepoint read from the IP header, be fed to ScreamRx for acknowledgment tracking, and then be passed to the RTP depacketizer for NAL unit reassembly. The challenge is that packets arrive with jitter, reordering, and gaps from loss. The depacketizer must handle incomplete frames gracefully, passing partial NAL units to the decoder with appropriate error flags rather than stalling the pipeline waiting for retransmission.

The third demand is RTCP feedback arriving at the vehicle from the operator station. Each feedback message updates SCReAM's view of the network, potentially changing the congestion window, pacing rate, and target bitrate in a single processing step. The feedback must be processed promptly because stale feedback leads to stale rate decisions, but the processing itself involves the most computationally intensive parts of SCReAM (OWD estimation, CWND update, rate allocation across streams). The adapter must ensure that feedback processing does not block the transmit path.

The fourth demand is session lifecycle management. When an operator initiates a session, the stack must construct and start GStreamer pipelines on both ends, establish UDP sockets with appropriate ECN configuration, initialize SCReAM sender and receiver instances, and begin the capture-encode-transmit loop. Teardown must release all resources cleanly. The challenge is that session startup should be fast (under 1 second from request to first displayed frame) while initializing hardware codecs, which have their own startup latency.

The fifth demand is network path changes. Cellular handovers cause the vehicle's IP address or port to change, requiring socket rebinding. Deep fades cause temporary connectivity loss lasting hundreds of milliseconds. The stack must detect these events, pause transmission during outages to avoid pointless packet loss, and resume quickly when connectivity returns. SCReAM's self-clocking naturally handles bandwidth changes (the congestion window drains during outages and refills when packets flow again), but the socket layer must cooperate by not discarding the send queue during brief outages.

## Solutions

On the vehicle side, when a raw camera frame is captured, [GStreamer Media Pipeline Adapter](media-pipeline-adapter.md) routes it through the pipeline: the v4l2src (or equivalent camera source) element delivers the frame to a capsfilter that enforces the target resolution and frame rate, then to [Hardware Video Codec Adapter](hardware-video-codec-adapter.md) which wraps the hardware encoder element. The encoder operates in constant-bitrate (CBR) mode with the target set by the most recent value from SCReAM Congestion Control Adapter. The encoder produces H.264 or H.265 NAL units that flow to the rtph264pay (or rtph265pay) GStreamer element, which fragments them into RTP packets. These packets then enter the gstscream element, which is where SCReAM Congestion Control Adapter takes control.

Inside the gstscream element, each RTP packet is pushed into SCReAM's RtpQueue via the standard queue interface. The adapter calls ScreamV2Tx::newMediaFrame() on each frame boundary (signaled by the RTP marker bit), registering the frame's size with the congestion controller. A transmit thread polls ScreamV2Tx::isOkToTransmit() in a loop: a return value of 0.0 means the next packet can be sent immediately, a positive value means wait that many seconds, and -1.0 means no packet is available. When transmission is authorized, the adapter calls addTransmitted() to record the packet in SCReAM's in-flight table and hands it to UDP ECN Transport Adapter.

UDP ECN Transport Adapter sends the packet through a UDP socket configured with the ECT(1) DSCP codepoint for L4S. The sendmsg() system call carries the packet to the operator station's network interface. On the receive side, the same adapter uses recvmsg() with IP_RECVTOS to extract the ECN bits from each arriving packet. The RTP payload is passed upstream to [GStreamer Media Pipeline Adapter](media-pipeline-adapter.md)'s depayloader, while the ECN bits and packet metadata (SSRC, sequence number, reception timestamp) are passed to RTCP Feedback Channel Adapter.

RTCP Feedback Channel Adapter wraps ScreamRx, calling receive() for each incoming RTP packet. ScreamRx records the packet's reception time and ECN status in its history buffer. Periodically (controlled by getRtcpFbInterval(), typically every 5-10ms depending on media bitrate), the adapter calls createStandardizedFeedback() to generate an RFC 8888 feedback message encoding the reception status of recent packets. This RTCP message is sent back to the vehicle over a UDP socket (either a separate port or multiplexed on the same socket).

When RTCP feedback arrives at the vehicle, RTCP Feedback Channel Adapter delivers the raw bytes to SCReAM Congestion Control Adapter, which calls ScreamV2Tx::incomingStandardizedFeedback(). This single call triggers the entire congestion control update: ACK processing (marking packets as received, computing OWD), loss detection (identifying gaps in the sequence number space), ECN processing (computing the marking fraction and updating l4sAlpha), CWND update (adjusting the congestion window based on loss, ECN, and delay signals), and rate allocation (dividing the new aggregate rate among streams). The updated target bitrate is then propagated back to [Hardware Video Codec Adapter](hardware-video-codec-adapter.md), which adjusts the encoder's rate control parameters. If ScreamV2Tx::getTargetBitrate() returns -1 (indicating detected loss), the codec adapter requests an immediate keyframe from the encoder to enable fast video recovery.

For session startup, [GStreamer Media Pipeline Adapter](media-pipeline-adapter.md) constructs the pipeline graph using GStreamer's element factory: on the vehicle, the chain is v4l2src -> capsfilter -> encoder -> rtppay -> gstscream -> udpsink; on the operator, it is udpsrc -> rtpdepay -> decoder -> autovideosink. The adapter pre-rolls the hardware encoder during pipeline construction so that the first frame can be encoded immediately when capture begins. UDP ECN Transport Adapter creates and binds the UDP sockets, configuring the IP_TOS option for ECT(1) marking. SCReAM Congestion Control Adapter instantiates ScreamV2Tx with parameters tuned for teleoperation: L4S enabled, queue delay target 60-100ms, pacing headroom 1.5x, and the stream registered with the target resolution's min/start/max bitrate range.

When a network path change is detected (via the cellular modem's API or by monitoring socket errors), UDP ECN Transport Adapter signals the disruption. During brief outages (under 500ms), the transmit thread continues polling isOkToTransmit() but the socket send fails silently; SCReAM's congestion window drains naturally as no ACKs arrive, and the RTP queue absorbs a small burst of frames. If the queue delay exceeds the threshold, SCReAM RTP Queue Management inside SCReAM clears the queue. When connectivity resumes, new ACKs restart the self-clocking loop and the CWND ramps back up. For longer outages or IP address changes, the adapter rebinds the socket and the session effectively restarts with SCReAM's initial slow-start behavior.

## Evaluation

The adapter architecture provides clear boundaries for testing and replacement. Each adapter can be unit-tested against its wrapped library's API independently: the SCReAM adapter can be tested with simulated network traces without a camera or display, the GStreamer adapter can be tested with test video sources without a real network, and the UDP adapter can be tested with loopback sockets without real cellular connectivity. Integration testing connects the adapters into the full pipeline and measures glass-to-glass latency.

The primary performance constraint is the hardware encoder's response time to bitrate changes. SCReAM updates its target bitrate every 20-50ms, but hardware encoders typically have a rate control loop that converges over several frames. This means the actual transmitted bitrate lags behind SCReAM's target by 2-5 frame periods (66-166ms at 30fps), creating a feedback delay that can cause oscillation when bandwidth changes rapidly. The Hardware Video Codec Adapter mitigates this by using the encoder's instantaneous rate control mode where available, and by applying SCReAM's adaptive target rate scaling (targetRateScale) to compensate for the encoder's tendency to undershoot or overshoot the target.

A secondary constraint is the GStreamer pipeline's internal buffering. GStreamer elements use asynchronous queues between threads, and each queue adds latency equal to the buffer depth. For teleoperation, queues must be configured with max-size-buffers=1 and leaky=downstream to prevent frame accumulation. The GStreamer clock must be configured in pipeline mode rather than element mode to ensure that the camera's capture timestamp propagates through the pipeline and is used for SCReAM's timing rather than the encoder's output timestamp.

The ECN support in the UDP adapter depends on kernel and network path support. Not all cellular networks pass ECN bits transparently; some middleboxes strip or remark ECN codepoints. When L4S is not available, SCReAM falls back to delay-based congestion detection (virtual CE events), which provides adequate performance but with higher steady-state queue delay than true L4S. The adapter should detect ECN blackholing (outgoing ECT(1) packets never receive CE marks even under congestion) and disable ECN to avoid confusing the congestion controller.

## Related Works

WebRTC provides an integrated real-time communication stack with its own congestion control (Google GCC), but its latency targets (150-400ms) are designed for conversational video rather than teleoperation. WebRTC's tight coupling between its codec, transport, and congestion control layers makes it difficult to substitute SCReAM for GCC. SRT (Secure Reliable Transport) offers an alternative transport protocol with ARQ-based recovery and configurable latency targets, but its retransmission approach adds at least one RTT per lost packet, which may exceed teleoperation budgets on cellular networks with 30-50ms RTT. RIST provides multi-path transport with ARQ, useful for fixed infrastructure but less suited to the single-path cellular scenario. The gstscream GStreamer plugin demonstrates that SCReAM integrates cleanly into GStreamer's pipeline model, validating the adapter approach used here. The Vay/Ericsson/Deutsche Telekom MWC 2023 demonstration used a similar architecture (SCReAM over 5G) for live vehicle teledriving, confirming the viability of this component selection for production teleoperation systems.

## Conclusion

[Teleoperation Video Streaming Stack](teleoperation-video-stack.md) bridges the gap between the conceptual architecture of Teleoperation Video Transport and a running system by selecting mature open-source components and connecting them through adapter interfaces. SCReAM Congestion Control Adapter brings SCReAM's self-clocking congestion control into the pipeline, governing the sending rate through the gstscream plugin's integration with [GStreamer Media Pipeline Adapter](media-pipeline-adapter.md). [Hardware Video Codec Adapter](hardware-video-codec-adapter.md) ensures that encoding and decoding latency does not dominate the end-to-end budget, while UDP ECN Transport Adapter provides the L4S-capable network layer that SCReAM needs for its lowest-latency operating mode. RTCP Feedback Channel Adapter closes the control loop by carrying reception reports back to the sender. The adapter pattern keeps the conceptual architecture stable while allowing each library choice to be revisited independently: SCReAM could be replaced with GCC, GStreamer with FFmpeg, or NVENC with VAAPI without restructuring the overall system.
